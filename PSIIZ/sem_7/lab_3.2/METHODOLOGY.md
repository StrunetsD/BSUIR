# Методика оценки безопасности кода (Lab 3.2)

Основана на результатах лабораторной работы № 3.1 (анализ кода + дампы RAM).

Каждый критерий: **2** — выполнено; **1** — частично; **0** — не выполнено.
Максимум: **20** баллов. Порог «приемлемо для учебного стенда»: ≥ 14.

| № | Критерий | Что проверять | Доказательства |
|---|----------|---------------|----------------|
| 1 | Разделение public / confidential | Есть разные типы данных и разная обработка | код, UI |
| 2 | Защита секрета при сохранении | Хеш и/или шифр сразу после ввода | store / snapshot |
| 3 | Валидация ввода | Пустые, длинные, некорректные значения → сообщение, не падение | UI / исключения |
| 4 | Минимизация plaintext в store | В структуре хранения нет исходного секрета | snapshot, поиск маркера |
| 5 | Безопасное удаление (логическое) | Delete убирает запись из структуры; желательно затирание полей | snapshot after_delete |
| 6 | Обработка ошибок | Нет утечки стека/ключей в UI; понятные сообщения | ручной тест |
| 7 | Ключ шифрования | Не хардкод в репозитории; генерируется в процессе (или из env) | код |
| 8 | Анализ RAM (инструменты) | Есть способ снять снимок (скрипт/дамп) create/update/delete | dumps/ |
| 9 | Наблюдаемость ресурсов | Можно оценить CPU/RSS (ps, getrusage, vmmap) | resources.txt |
| 10 | Документированность угроз | Понятно, что plaintext может остаться в виджете/куче | README / отчёт |

## Как применять

1. Разобрать код по критериям 1–7, 10.  
2. Прогнать сценарий: create → dump → update → dump → delete → dump; поиск маркеров.  
3. Выставить баллы, кратко обосновать.  
4. Сравнить два варианта по одной таблице.

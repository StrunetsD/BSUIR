## 1. Препроцессинг (NLP, английский)

Конвейер идентичен для документа и запроса (ПОД и ПОЗ одной структуры —
требование лабы):

1. lowercase, нормализация unicode;
2. токенизация: `[a-z]+(?:'[a-z]+)?` (regex), пунктуация отбрасывается;
3. стоп-слова: список NLTK `english` (~179 слов);
4. лемматизация: NLTK `WordNetLemmatizer`, pos=NN→'n', VB→'v', JJ→'a',
   RB→'r' (наивный pos-tagging по суффиксам допустим — или `pos_tag` NLTK);
5. фильтр: длина ≥ 2, не чисто цифры.

Результат: список лемм. Порядок сохраняется (нужен для фразового режима).

## 2. Индексация (класс `Document`)

### 2.1 Инверсная частота термина — формула (1.5)

```
B_i = log( N / P_i )
```
- `N` — число документов в базе;
- `P_i` — число документов, содержащих термин i (`terms.doc_freq`);
- логарифм натуральный (фиксируем: `math.log`).

### 2.2 Вес термина в документе — формула (1.6)

```
A_i^j = Q_i^j × B_i
```
- `Q_i^j` — частота (tf) леммы i в документе j;
- `A_i^j` → `postings.tfidf_weight`.

### 2.3 Нормированное TF-IDF представление (векторная модель лабы)

```
w_dk = N_dk · log(N/N_k) / sqrt( Σ_j (N_dj · log(N/N_j))² )
```
- `N_dk` — встречи k-го термина в документе d; `N_k` — документов с термином;
- знаменатель — евклидова норма «сырых» весов документа;
- → `postings.tfidf_norm`; вектор документа = sparse-словарь
  `{term_id: tfidf_norm}` = `Document.get_document_vector(document_id)`.

## 3. Поиск (класс `Search`)

Поля лабы: `all_words_together: bool`, `date_start/date_end: str|None`,
`search_query: str`. Пять стратегий — переключаются параметром `model`.

### 3.1 Boolean (`model=boolean`)

- вектор запроса бинарный: `q_j = 1, если термин j ∈ запросе` (формула 1.8);
- по умолчанию **OR**: r = документы, содержащие ≥1 термин запроса;
- `all_words_together=true` → **AND**: все термины присутствуют
  (фразовый порядок не проверяем — фиксируем: «все слова вместе» = AND);
- ранжирование результата: по числу совпавших терминов, затем по дате.

### 3.2 TF-IDF + косинус (`model=tfidf`) — формулы (1.7), (1.8)

Матрица L (N×D) строками имеет поисковые образы документов (1.7);
обращение к системе `L × q = r` (1.8), мера схожести — косинус:

```
r(D, Q) = (D, Q) / (||D|| · ||Q||)
```

- D — вектор документа (tfidf_norm, §2.3);
- Q — вектор запроса: веса `w_qk = tf_qk · idf_k`, нормированные тем же
  способом (нормировка не меняет косинус, но фиксируем её для отчёта);
- private-методы лабы: `scalar_product(a, b)`, `euclidean_norm(a)` —
  реализуются над sparse-словарями `{int, float}` (рис. 2 лабы).

### 3.3 Вероятностная модель — BM25 (основная, вариант 11)

Okapi BM25 — практическая реализация вероятностной модели (RSJ):

```
score(D, Q) = Σ_i IDF(qi) · f(qi, D)·(k1+1) / ( f(qi, D) + k1·(1 − b + b·|D|/avgdl) )

IDF(qi) = ln( (N − n(qi) + 0.5) / (n(qi) + 0.5) + 1 )
```
- `f(qi, D)` — tf в документе; `|D|` — длина документа (в леммах);
  `avgdl` — средняя длина; `n(qi)` — doc_freq;
- параметры: **k1 = 1.2, b = 0.75** (стандарт);
- теоретическая база RSJ (Binary Independence Model):
  `w_i = log( p(1−r) / ((1−p)·r) )`, при p=0.5 и оценке r через doc_freq
  вырождается в IDF-член — это связывает BM25 с (1.5); описать в отчёте.

### 3.4 Dense (`model=dense`)

- эмбеддинг запроса тем же провайдером, что и документы (mistral-embed, 1024);
- сходство: cosine = `1 − cosine_distance`, поиск по HNSW-индексу pgvector;
- запрос `ORDER BY embedding <=> $1 LIMIT k` (`<=>` = cosine distance).

### 3.5 Hybrid (`model=hybrid`)

Reciprocal Rank Fusion поверх BM25 и Dense:

```
RRF(d) = Σ_{s ∈ {bm25, dense}} 1 / (60 + rank_s(d))
```
- `rank_s(d)` — позиция документа в выдаче стратегии s (1-based);
- документ, отсутствующий в одной из выдач, вклад по этой стратегии = 0;
- финальная сортировка по RRF по убыванию.

### 3.6 Формирование SearchResult (рис. 3 лабы)

| Поле | Правило |
|---|---|
| `document_id` | id из БД |
| `title` | documents.title |
| `snippet` | **первые 300 символов** текста (требование лабы), обрезка по границе слова + `…` |
| `rank` | score стратегии, double; у boolean — count совпавших терминов |
| `date` | published_at (ISO) |
| `matched_terms` | леммы запроса, реально присутствующие в документе (расширение — требование лабы «список слов запроса присутствующих в документе») |
| `highlight` | позиции для подсветки в UI (по matched_terms, включая словоформы через общий лемматизатор) |

Плюс фильтры: `date_start ≤ published_at ≤ date_end` (если заданы), `top_k`.

## 4. Оценка качества → см. [METRICS.md](METRICS.md)

Метрики считаются **только** по результатам, ранжированным по убыванию
`rank` конкретной стратегии. Релевантность бинарная: qrels `grade ≥ 2`;
NDCG использует градации 0–3 напрямую.

## 5. Edge-cases (обязательные unit-тесты)

1. Пустой запрос / запрос только из стоп-слов → пустая выдача, HTTP 200.
2. Термин запроса отсутствует в словаре → игнорируется (не ошибка).
3. Документ нулевой длины (после препроцессинга) — не индексируется.
4. `log(N/P)` при P=N → idf=0; документ-вектор не содержит нулевых весов.
5. Дубликаты слов в запросе → считаются один раз (tf запроса = 1 для
   boolean/bm25-idf; для tfidf-Q допускается tf — фиксируем: **1**).
6. Один документ в базе → avgdl = |D|, BM25 валиден.
7. all_words_together + термин вне словаря → AND даёт пустую выдачу.
